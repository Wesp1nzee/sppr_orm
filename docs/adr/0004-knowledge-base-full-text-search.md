# ADR 0004: Полнотекстовый поиск по базе знаний (tsvector) и деградация на SQLite

- Статус: принято
- Дата: 2026-08-29

## Контекст

ТЗ требует полнотекстовый поиск по нормам и определениям КС РФ с фильтрацией
по номеру документа, дате и ключевым словам, а также просмотр текста акта с
выделением релевантных фрагментов. Продакшен СУБД — PostgreSQL 18 (есть нативные
`tsvector`, `websearch_to_tsquery`, `ts_rank`, `ts_headline`), но основной набор
тестов гоняется на in-memory SQLite (`aiosqlite`), где этих функций нет. В модели
`NormativeDocument` нет поля с датой принятия акта в реальном мире.

## Решение

1. **«Фильтр по дате» = `created_at` записи в БЗ.** Дата принятия нормативного
   акта в модели отсутствует; добавлять её в эту итерацию не требуется — разумная
   трактовка ТЗ покрывается датой появления версии в базе знаний (`created_at`).
   Опциональное поле `document_date` остаётся fast-follow (отдельной миграцией),
   если по смыслу ТЗ понадобится реальная дата акта.

2. **Кросс-диалектный тип `TSVECTOR` — через `with_variant`, а не `TypeDecorator`.**
   Проект уже использует паттерн `JSON().with_variant(PGJSONB, "postgresql")` в
   `app/db/base.py`; по аналогии добавлен
   `Text().with_variant(PGTSVECTOR, "postgresql")`. Это отклонение от
   первоначального замысла (отдельный `TypeDecorator`): `with_variant` точнее
   повторяет существующий в проекте паттерн для `JSONB` и короче, не ломая
   единый стиль. На SQLite колонка — обычный `Text`, не участвует в поиске.

3. **`search_vector` заполняется на уровне приложения при `create_new_version`.**
   Не через `GENERATED ALWAYS AS` — чтобы избежать рассинхронизации с диалектами
   в тестах и контролировать словарь `'russian'`. В `INSERT` подставляется
   `func.to_tsvector('russian', title || full_text || summary)` (только на
   Postgres; на SQLite колонка остаётся `NULL`). Backfill существующих строк —
   в миграции `6f8baca81cf7`.

4. **SQLite-деградация поиска — `LIKE` по `title`/`full_text`/`summary`.**
   Диалект определяется через `session.bind.dialect.name`. На Postgres запрос
   фильтруется через `search_vector @@ websearch_to_tsquery('russian', query)` и
   сортируется по `ts_rank(...)`; на SQLite — `ilike` (компилируется в
   `lower(x) LIKE lower(y)`) и сортировка по `code` (релевантность недоступна,
   корректность набора результатов сохраняется). Ограничение: `lower()` в SQLite
   понимает только ASCII, поэтому кириллица на SQLite сопоставляется с учётом
   регистра — это осознанная деградация тестового контура, на проде (Postgres)
   регистронезависимость обеспечивает FTS.

5. **Выбран `websearch_to_tsquery`, а не `to_tsquery`.** Он терпим к
   произвольному пользовательскому вводу и не требует ручного экранирования
   спецсимволов `&`/`|`/`!`, поэтому отдельная обёртка в
   `AppException(VALIDATION_ERROR)` не нужна. `query` дополнительно ограничен
   `max_length=256` и трактуется как «нет поиска», если пуст после `strip()`.

6. **Хайлайтинг: `ts_headline` на Postgres, ручное окно на SQLite.**
   На Postgres `ts_headline('russian', full_text, query, 'StartSel=<mark>,
   StopSel=</mark>, MaxFragments=3, ...')` возвращает готовые фрагменты с
   `<mark>`. На SQLite точная реплика `ts_headline` — отдельная большая задача,
   поэтому реализована честная деградация: первое регистронезависимое вхождение
   `query` в Python + окно ±150 символов с ручной вставкой `<mark>...</mark>`.
   В коде это помечено как SQLite-деградация, а не эталон.

## Обоснование

- **Нативный FTS** — единственный вариант с приемлемым качеством и скоростью на
  большом объёме юридических текстов; `LIKE` по всему корпусу не масштабируется.
- **`with_variant`** минимизирует расхождение с существующим кодом и не вводит
  новый механизм в проект.
- **Деградация вместо падения** сохраняет полный стек HTTP-тестов без внешнего
  PostgreSQL и явно документирует, что на SQLite качество ранжирования ниже.
- **`websearch_to_tsquery`** убирает класс ошибок, связанных с экранированием
  пользовательского ввода.

## Последствия

- `NormativeDocument` получает nullable-колонку `search_vector` (GIN-индекс
  `ix_normdoc_search_vector` на Postgres).
- `create_new_version` обязан заполнять `search_vector` на Postgres; на SQLite —
  нет (деградация берёт текст из исходных колонок).
- Ранжирование по релевантности и `ts_headline` не воспроизводимы на SQLite и
  покрываются отдельным интеграционным тестом на реальном PostgreSQL
  (`make test-integration`).
