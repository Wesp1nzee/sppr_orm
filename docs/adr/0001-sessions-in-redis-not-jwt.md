# ADR 0001: Серверные сессии в Redis вместо JWT

- Статус: принято
- Дата: 2026-08-26

## Контекст

Нужен механизм аутентификации для SPA-фронтенда. Рассматривались два варианта:
stateless JWT в HttpOnly-cookie и серверные сессии с идентификатором в cookie.

## Решение

Использовать серверные сессии в Redis: клиенту выдаётся HttpOnly-cookie `sid`
(неподписанный случайный идентификатор), а само состояние сессии (user_id,
role, issued_at, hard_expire_at) хранится в Redis под ключом `session:{sid}`
со скользящим TTL 30 минут и жёстким лимитом 12 часов (`app/auth/service.py`).

## Обоснование

- **Отзыв сессии**: удаление ключа в Redis мгновенно разлогинивает пользователя
  (например, при деактивации аккаунта — `app/auth/dependencies.py`).
- **Нет проблемы revocation**: JWT остаётся валидным до истечения срока, и
  отозвать его без чёрного списка нельзя.
- **Жёсткий лимит сессии** (`hard_expire_at`) защищает от «вечных» сессий даже
  при скользящем продлении TTL.
- **Простота**: Redis уже используется в проекте (см. `README.md`, раздел
  «Стек»: «Auth: сессии в Redis + HttpOnly cookie sid ... (без JWT)»).

## Последствия

- Аутентификация требует доступности Redis (добавляет внешнюю зависимость для
  каждого запроса с проверкой сессии).
- Инстансы приложения разделяют состояние через общий Redis.
- Заголовок `Authorization` не используется — фронт полагается на cookie и
  `credentials: 'include'`.
