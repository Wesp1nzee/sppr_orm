# ADR 0003: Модель журнала аудита и синхронная запись из EventBus

- Статус: принято
- Дата: 2026-08-28

## Контекст

ТЗ (разделы 3.5, 4) требует полного протоколирования работы системы и хранения
журнала действий не менее 1 года. События доменов уже публикуются в `EventBus`,
но подписчик `audit` был заглушкой (только `logging`). Нужно было решить: форму
хранения события, как фиксировать роль и IP, и как записывать события, не
блокируя HTTP-ответ.

## Решение

1. **Одна таблица `audit_log_entries` (append-only).** Каждое событие — строка:
   `event_type`, `user_id` (FK `ON DELETE SET NULL`), снимок `user_role`, `payload`
   (JSONB) и `ip_address`. Без `updated_at` — записи неизменяемы; от наследуемого
   столбца `Base.updated_at` модель осознанно отказывается (`updated_at = None`).

2. **`payload` = сериализованный dataclass события.** `dataclasses.asdict(event)`
   с рекурсивным приведением к JSON-совместимым типам (`UUID → str`,
   `Enum → value`). Никакого универсального `repr()`: у каждого типа события свой
   тонкий обработчик (`event_type` + `payload`).

3. **Роль — отдельным запросом по `user_id`.** Подписчик резолвит `user_role`
   через `UserRepository.get_by_id(user_id)` на момент обработки события, а не
   протаскивает её через каждое событие. В сессии запроса `session.get` видит
   flush-нутого пользователя из identity map, поэтому роль корректна и для
   `UserRegistered` (событие публикуется до commit источника).

4. **Запись — в сессию запроса (лёгкий outbox), иначе — в собственную.** Через
   `app/core/request_context.py` (`ContextVar`) `get_db` публикует активную
   `AsyncSession` запроса; подписчик пишет в неё (без commit — коммитит `get_db`),
   поэтому аудит атомарен с транзакцией источника и FK на `users.id`
   удовлетворяется даже для не закоммиченного пользователя. Вне запроса (будущая
   очередь, скрипты) открывается собственная сессия из `async_session_factory`.
   `EventBus.publish` — fire-and-forget (глотает и логирует исключения).

5. **`ip_address` заполняется из `request_context`.** `ContextVar[str | None]`
   устанавливается middleware в `app.main` из `request.client.host`; подписчик
   читает его и пишет в поле `ip_address` (вне запроса — `None`).

6. **Ретеншен — без фонового воркера.** `AuditService.purge_expired()` +
   CLI-скрипт `scripts/purge_audit_log.py`, запускаемый снаружи приложения
   (cron/systemd-таймер). Асинхронная очередь (ARQ/Redis) ещё не реализована —
   seam оставлен через интерфейс `AuditWriter` (`app/audit/subscribers.py`).

## Обоснование

- **Append-only** соответствует природе журнала аудита (неизменяемая история).
- **`ON DELETE SET NULL`** сохраняет запись при удалении пользователя (требование
  неразрывности журнала).
- **Снимок роли, а не FK** — роль может измениться после события; журнал должен
  фиксировать её на момент события.
- **Синхронная запись** проста и достаточна на текущем этапе; `AuditWriter`
  позволит позже перейти на очередь без изменения сигнатур подписчиков.
- **`asdict` + JSON-нормализация** избегает ручного маппинга каждого события и
  ошибок сериализации `UUID`/`Enum` в JSONB.

## Последствия

- Модель `AuditLogEntry` не наследует `updated_at` от `Base`.
- Аудит пишется в транзакции источника (при её откате откатывается и запись) —
  в отличие от исходной схемы с отдельной сессией, которая теряла `UserRegistered`
  из-за `ForeignKeyViolationError` (пользователь ещё не закоммичен).
- `ip_address` заполняется только в рамках HTTP-запроса; события из скриптов/очереди
  получают `None`.
