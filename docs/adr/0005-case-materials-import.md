# ADR 0005: Импорт материалов дела (PDF/DOCX) → черновик проверки

- Статус: принято
- Дата: 2026-08-29

## Контекст

ТЗ, раздел 4 «Интеграция», требует импорт материалов дела в форматах PDF и
DOCX. UC-1, шаг 2 допускает либо загрузку файла, либо ручной ввод через мастер
проверки — то есть импорт является *альтернативой* ручному вводу, а не заменой
его. Реальный заполненный образец материалов от заказчика отсутствует; в
распоряжении только референсный PDF пустых бланков
(`docs/samples/case_materials_blank_forms.pdf`, 14 типовых оперативно-служебных
форм ОРД: рапорт, постановление о проведении ОРМ, распоряжение об обследовании,
протоколы досмотра/вручения/изъятия и т.д.). Поэтому решения ниже принимаются
по неполным данным и **подлежат пересмотру при получении реального образца от
заказчика**.

## Допущения (зафиксированы, подлежат пересмотру)

1. **[ДОПУЩЕНИЕ 1] Только машиночитаемый текст, без OCR.** Извлекаем текст из
   цифровых PDF (текстовый слой, `pypdf`) и DOCX (`python-docx`, уже используется
   в `app/documents/export.py`). Распознавание сканов/рукописного текста (OCR,
   `tesseract`) в этой итерации не реализуется: это отдельная дорогая задача с
   низкой точностью на рукописных юридических текстах. Если текст после
   извлечения пуст или почти пуст (эвристика: среднее число символов на страницу
   ниже `MIN_TEXT_CHARS_PER_PAGE = 40`), материал получает статус
   `text_extraction_failed` и понятное сообщение, но запрос не падает — пользователь
   продолжает через ручной ввод. Точка расширения — протокол `TextExtractor`
   (`PdfTextExtractor`/`DocxTextExtractor`), к которому позже добавится
   `OcrTextExtractor`.

2. **[ДОПУЩЕНИЕ 2] Импорт = черновик для подтверждения.** `Check` никогда не
   создаётся автоматически: пайплайн «загрузка → извлечение → распознавание →
   черновик → правка/подтверждение пользователем → `CheckService.create`».
   Создание проверки происходит только по явному `POST /case-materials/{id}/confirm`,
   тем же путём, что и ручной ввод. Осознанный выбор в пользу безопасности
   юридического ПО.

3. **[ДОПУЩЕНИЕ 3] Локальное файловое хранилище.** Клиента объектного хранилища
   (S3/MinIO) в проекте нет. Файл хранится на диске в директории
   `settings.case_materials_storage_dir` (добавлена в `app/core/config.py` и
   `docker-compose.yml` как зарезервированный volume), в БД — только метаданные
   (путь, имя, MIME, размер, SHA-256 для идемпотентности) и результат извлечения.
   Ограничения: размер до 25 МБ (`MAX_UPLOAD_BYTES`) и два допустимых MIME-типа —
   отклонение происходит до чтения файла.

4. **[ДОПУЩЕНИЕ 4] MVP — приоритетные типы, не все 14 форм.** Структурное
   извлечение полей реализовано только для 3 типов (обоснование ниже); для
   остальных — только распознавание типа по заголовку + полный текст для ручного
   просмотра.

5. **[ДОПУЩЕНИЕ 5] Извлечение полей — по меткам-якорям, не NLP/LLM.** Бланки
   построены по шаблону «заголовок + именованные поля-прочерки». Извлечение — через
   регулярные выражения/якоря (`capture_anchor`), каждый результат несёт пометку
   уверенности `confidence: "high" | "low"` (`ExtractedField.is_confident`).

## Обоснование выбора приоритетных типов (Допущение 4)

Приоритет выбран по критериям `app/checks/rules/criterion_01..14.py`: какие поля
материалов реально влияют на результат проверки. Анализ показал:

- **`resolution_to_conduct_orm`** (постановление о проведении ОРМ) — даёт вид ОРМ
  (`orm_type`, критерий 13) и основание/поручение (критерий 1), фиксирует правовое
  основание (ст. 7 ФЗ).
- **`inspection_order`** (распоряжение о гласном ОРМ «обследование помещений») —
  даёт `premises_type` (жилое/нежилое) и отметку об ознакомлении
  (`residents_consent`), напрямую влияет на критерии 3 и 6 (обследование жилого
  помещения без согласия/судебного решения).
- **`search_protocol`** (протокол досмотра до/после ОРМ) — фиксирует «досмотр» как
  вид ОРМ (критерий 13) и наличие незаинтересованных лиц (ст. 17 ФЗ), релевантное
  процедурным критериям.

Остальные 10 форм (рапорт, заявление о согласии, протоколы вручения/изъятия СТС,
обследования ТС, постановления о рассекречивании/представлении результатов и т.д.)
на этой итерации только распознаются по заголовку — пользователь читает текст и
вводит данные вручную. Это не деградация ниже ТЗ (импорт работает для всех типов),
а разумное ограничение глубины автозаполнения.

## Решение

1. **Новый домен `app/case_materials`** по шаблону остальных доменов
   (Protocol-репозиторий + сервис + роутер + `ApiRouter`/`DataResponse`).

2. **Модель `CaseMaterialUpload`** — метаданные файла + `status` (enum
   `uploaded`/`processing`/`extracted`/`text_extraction_failed`/`failed`),
   `extracted_text` (Text), `detected_documents` (JSONB — сегменты с типом,
   позициями и полями), `suggested_check_answers` (JSONB — черновик в формате
   `CheckCreateRequest.answers`), `error_message`. `user_id` — FK `CASCADE`
   (материалы принадлежат пользователю, в отличие от журнала аудита).

3. **Сегментация** — `DocumentSegmenter` разбивает текст по заголовкам известных
   типов (сопоставление по регэкспу, не по точному строковому совпадению — реальные
   файлы могут отличаться форматированием).

4. **Экстракторы полей** — по одному модулю на тип
   (`app/case_materials/fields/{resolution,inspection_order,search_protocol}.py`),
   реестр `FIELD_EXTRACTORS` по образцу `app/checks/rules/registry.py`.

5. **Синхронное извлечение в рамках запроса.** Фоновой очереди нет
   (`app/workers/README.md` — только контракт). Если извлечение окажется медленным
   на больших файлах — известное ограничение, не вводим ARQ в этой итерации.

6. **Событие `CaseMaterialUploaded`** публикуется в `EventBus` и пишется в журнал
   аудита подписчиком `app/audit/subscribers.py` (переиспользуем инфраструктуру).

7. **Confirm** создаёт `Check` через существующий `CheckService.create` (без
   дублирования логики критериев); при неготовом материале — `409
   CASE_MATERIAL_NOT_READY`.

## Последствия

- Новая таблица `case_material_uploads` (миграция Alembic).
- `pypdf` добавлен в зависимости (`uv add pypdf`); `python-docx`/`reportlab` уже
  были в проекте.
- Новые коды ошибок: `CASE_MATERIAL_NOT_FOUND` (404), `CASE_MATERIAL_FILE_TOO_LARGE`
  (400), `CASE_MATERIAL_UNSUPPORTED_FORMAT` (400), `CASE_MATERIAL_NOT_READY` (409) —
  с локализацией ru/en в `app/core/messages.py`.
- OCR-пайплайн и разбор оставшихся 10 форм — fast-follow по реальному образцу.
- `settings.case_materials_storage_dir` и volume `case_materials_data` зарезервированы
  под будущий сервис приложения в docker-compose.
